# LEARNING_05.md — библиотека тайлов и варианты Персонажа на QML

Это продолжение курса после [`LEARNING_04.md`](LEARNING_04.md). Практический проект — изучить и расширить библиотеку визуальных компонентов игровых тайлов и вариантов Персонажа, сравнить оформление в галерее и подключить его к Boulder Dash. Базовая реализация уже есть в репозитории; упражнения ниже предлагают проследить её работу и добавить собственные варианты. По пути разбирается полный путь изменения: действие игрока вызывает метод `GameEngine`, движок меняет данные, модель посылает уведомление, а QML обновляет тайл, Персонажа или HUD.

## Цель

Научиться находить ошибки на границе C++ и QML и создавать повторно используемые QML-компоненты. Если очки изменились в C++, но не обновился HUD, проблема обычно в уведомлении свойства. Если изменился символ карты, но картинка осталась прежней, проверьте модель и её сигнал `dataChanged`. Если Персонаж визуально не движется, проверьте привязки `x`, `y` и `playerPositionChanged`.

В проекте есть два разных канала обновления интерфейса:

1. **Свойства `GameEngine`.** Например, `score`, `playerX`, `hasKey`. QML читает их как `gameEngine.score`; после изменения C++ должен испустить указанный в `Q_PROPERTY` сигнал `NOTIFY`.
2. **Модели списков.** `tilesModel` и `enemiesModel` — объекты `QAbstractListModel`. QML получает их роли через `Repeater`; изменение одной записи модели должно сообщить об этом через `dataChanged`, а полная замена списка — через `beginResetModel()` / `endResetModel()`.

Оба канала описывают отображение состояния. Источником игровых правил остаётся C++-движок; не создавайте в QML вторую независимую копию карты или счёта.

## 1. Проследите движение Персонажа

Начните с нажатия клавиши:

```text
Keys.onPressed в qml/main.qml
  → gameEngine.movePlayer(dx, dy)
  → изменение m_playerX и m_playerY в src/gameengine.cpp
  → emit playerPositionChanged()
  → обновление x и y компонента Player в qml/main.qml
```

Метод доступен QML благодаря `Q_INVOKABLE`. Свойства `playerX` и `playerY` объявлены через `Q_PROPERTY` с `NOTIFY playerPositionChanged`. Компонент `Player.qml` не знает правил столкновения: его координаты привязаны к свойствам движка.

Привязка QML выглядит так:

```qml
Player {
    size: root.tileSize
    variant: root.playerVariant
    x: gameEngine.playerX * root.tileSize
    y: gameEngine.playerY * root.tileSize
    state: gameEngine.playerState
    facingRight: gameEngine.playerFacingRight
}
```

Если после хода значение `playerX` изменилось, но спрайт стоит, проверьте правильность `NOTIFY` сигнала и отсутствие императивного присваивания `player.x` в другом месте. Такое присваивание может разорвать декларативную привязку.

### Упражнение 5.1 — проследить одно действие

Выберите ход Персонажа и найдите его путь в коде от нажатой клавиши до изображения. Запишите файлы, функции и сигнал в порядке вызова.

**Критерий готовности:** можете объяснить, почему ход блокируется, где меняются координаты и какое уведомление заставляет QML переместить компонент.

## 2. Проследите изменение клетки

Карта хранится в `GameEngine::m_grid`, а визуальные типы клеток — в `TileModel`. Например, при копании символ Кирпича `#` заменяется на `.`; модель обновляется типом `dug`. При восстановлении символ снова становится `#`, а тип модели — `brick`.

В `TileModel` определены роли:

```cpp
enum Roles { RowRole = Qt::UserRole + 1, ColRole, TypeRole };

QHash<int, QByteArray> roleNames() const override {
    return {
        {RowRole, "row"},
        {ColRole, "col"},
        {TypeRole, "type"}
    };
}
```

`roleNames()` задаёт имена, которые видит QML. `Repeater` создаёт для каждой записи `Tile`, координаты и вид которого читаются из ролей:

```qml
Repeater {
    model: gameEngine.tilesModel
    delegate: Tile {
        x: model.col * root.tileSize
        y: model.row * root.tileSize
        type: model.type
        size: root.tileSize
        theme: root.tileTheme
    }
}
```

Метод `TileModel::updateTile()` меняет тип записи и испускает `dataChanged` для роли `TypeRole`. Если поменять `m_grid`, но забыть обновить модель, физика и картинка разойдутся. Если обновить только модель, а не `m_grid`, игрок увидит один объект, а правила столкновения будут считать другой.

### Упражнение 5.2 — проверить уведомление модели

1. Найдите путь копания от `GameEngine::dig()` до `TileModel::updateTile()`.
2. Найдите путь восстановления Кирпича из `startDugTileTimer()`.
3. Проверьте в `Tile.qml`, как типы `brick` и `dug` влияют на отрисовку.
4. В тесте наблюдайте `dataChanged` через `QSignalSpy` и проверьте, что при изменении типа модели приходит одно уведомление.

**Критерий готовности:** тест различает изменение внутренней карты и уведомление визуальной модели; после копания и восстановления вид тайла соответствует игровому правилу.

## 3. Свойства и сигнал `NOTIFY`

`Q_PROPERTY` описывает мост между C++-значением и QML:

```cpp
Q_PROPERTY(int score READ score NOTIFY scoreChanged)
```

`READ score` сообщает, как прочитать значение. `NOTIFY scoreChanged` сообщает QML, когда перечитать его. Сигнал не заменяет значение: сначала движок изменяет поле, затем испускает уведомление.

В HUD используется декларативное выражение:

```qml
text: qsTr("Очки: %1").arg(gameEngine.score)
```

При сборе Приза движок добавляет очки и испускает `scoreChanged`; QML сам пересчитывает текст. Не присваивайте текст HUD вручную после каждого действия: это дублирует реактивную связь.

У одного сигнала может быть несколько связанных свойств. Например, `scoreChanged` используется для счёта, рекорда, жизней и оставшихся Призов. Когда добавляете свойство или меняете существующее, проверьте, что сигнал испускается во всех путях изменения значения: копание, таймер, сбор награды, перезапуск и смена уровня.

### Упражнение 5.3 — найти пропущенное уведомление

Выберите одно `Q_PROPERTY` в `gameengine.h`. Найдите все места, где соответствующее поле меняется, и проверьте, что каждое изменение сопровождается нужным сигналом. Добавьте или расширьте тест с `QSignalSpy` для наиболее важного сценария.

**Критерий готовности:** значение и сигнал проверяются отдельно: тест подтверждает новое значение и ожидаемое число уведомлений.

## 4. Виджет QML не должен владеть правилами игры

`Tile.qml` выбирает представление клетки и передаёт ему визуальные свойства. Для Кирпича, Кристалла и обычного Приза отрисовка вынесена в компоненты `qml/components/tiles/`; остальные типы пока рисуются в `Tile.qml`. `GameEngine` отвечает за то, можно ли войти в клетку, начисляются ли очки и когда таймер восстанавливает Кирпич. Например, `dug` отображается как пустая клетка, но проходимость определяется картой движка, а не цветом делегата.

Полезное разделение вопросов:

| Наблюдение | Где искать причину |
|---|---|
| Персонаж не может войти в клетку | `playerCanEnter()` и символ в `m_grid`. |
| Игрок вошёл, но картинка клетки старая | `TileModel::updateTile()` и `dataChanged`. |
| Счёт изменился в C++, но не в HUD | `Q_PROPERTY`, `NOTIFY` и `scoreChanged`. |
| Вид тайла неверный, но модель содержит правильный тип | `Tile.qml`, свойство `type` и условие `visible`. |
| Уровень изменился, но размер игрового поля старый | свойства `rows`/`columns` и `levelChanged`. |

## 5. Порядок диагностики

Когда визуальный результат не соответствует ожиданиям, проверяйте слои по порядку:

1. **Ввод:** получил ли `gameRoot` клавиатурное событие? У него должны быть `focus: true` и подходящий обработчик.
2. **Вызов:** был ли вызван нужный `Q_INVOKABLE` метод?
3. **Правило:** разрешают ли игровые данные действие? Проверьте координаты, символ клетки и условие столкновения.
4. **Состояние:** изменилось ли значение в `GameEngine` или `m_grid`?
5. **Уведомление:** испущен ли `NOTIFY` сигнал либо сигнал модели `dataChanged`?
6. **Представление:** получает ли QML правильное свойство/роль и рисует ли `Tile.qml` соответствующий тип?

Такой порядок отделяет «ход запрещён игровым правилом» от «ход состоялся, но интерфейс не обновился». Не исправляйте картинку, пока не выяснили, какое состояние хранит движок.

## 6. Ручная проверка интерфейса

Qt Test проверяет значения и сигналы, но не заменяет визуальный запуск. После изменений QML вручную проверьте:

- ход в каждую сторону и поворот каждого варианта Персонажа;
- переключение темы и героя без сброса позиции, счёта и текущего действия;
- копание, вход в яму, выход и восстановление Кирпича;
- обновление очков, Призов, жизней и Ключа в HUD;
- уведомления о Ключе, Сейфе и конце игры;
- разные размеры окна и отсутствие обрезания текста или тайлов.

Проверьте вывод приложения на сообщения `QML` об ошибках привязки, неизвестных свойствах и типах. Ошибка в консоли часто указывает на неверное имя роли или свойства ещё до ручного поиска по экрану.

## Практический проект — библиотека тайлов и Персонажей

В проекте уже реализованы три темы тайлов, четыре варианта Персонажа и общая галерея. Источник графики — локальные наборы Kenney: Pixel Platformer, Blocks и Industrial Expansion. Они содержат PNG, а повторно используемые QML-компоненты созданы в этом проекте.

### Этап A — изучить каталог графики

Выбранные файлы и лицензии перечислены в [каталоге Kenney](assets/tilesets/kenney/README.md). Для тайлов используются изображения 18×18, для Персонажей — 24×24 из `pixel-platformer/Tiles/Characters/`. Размер клетки игры — 32×32. Не переносите размер тайлов автоматически на спрайты Персонажа: сверяйтесь с PNG и соответствующей таблицей `Tilesheet*.txt`.

| Представление | Источник относительно `assets/tilesets/kenney/` |
|---|---|
| Kenney: Кирпич | `pixel-platformer/Tiles/tile_0006.png` |
| Kenney: Кристалл | `pixel-platformer/Tiles/tile_0067.png` |
| Kenney: Приз | `pixel-platformer/Tiles/tile_0151.png` |
| Industrial: Кирпич | `pixel-platformer-industrial-expansion/Tiles/tile_0038.png` |
| Industrial: Кристалл — синий индикатор | `pixel-platformer-industrial-expansion/Tiles/tile_0065.png` |

| Дополнительный вариант Blocks | `pixel-platformer-blocks/Tiles/Stone/tile_0000.png` |

Все выбранные изображения имеют альфа-канал и распространяются по CC0; файлы `License.txt` сохранены в каталогах наборов. Отдельный тайл Blocks показан как кандидат для будущей темы, в игровом переключателе его пока нет.

Визуально проверьте `Preview.png`, отдельный PNG и результат масштабирования. Для резких пиксельных границ используется:

```qml
Image {
    width: 32
    height: 32
    source: "qrc:/assets/tilesets/kenney/pixel-platformer/Tiles/tile_0006.png"
    fillMode: Image.PreserveAspectFit
    smooth: false
    mipmap: false
}
```

Этот путь уже включён в [`qml.qrc`](qml.qrc). Ресурсный alias должен совпадать с URL в QML. Прозрачные поля внутри PNG тоже масштабируются: два изображения одинакового размера файла могут выглядеть по-разному по высоте.

**Критерий готовности:** можете найти исходник каждого представления, его размер и лицензию и объяснить, почему фон превью не должен попадать в игровой ресурс.

### Тип объекта и его представление — разные данные

Символы уровней (`#`, `C`, `$`) задают игровые правила. Движок преобразует их в семантические типы модели (`brick`, `crystal`, `gold`). QML получает тип и выбирает изображение. Оформление не меняет символ клетки или физику.

```qml
Tile {
    type: model.type
    size: root.tileSize
    theme: root.tileTheme
}
```

`theme` имеет значения `classic`, `kenney`, `industrial`. Это строковый выбор среди нескольких вариантов; флаги `highlighted` и `animated` отвечают за отдельные визуальные возможности.

### Упражнение 5.4 — проследить представление объекта

Проследите Кирпич от `#` в карте до `brick` в модели, `Loader` в `Tile.qml`, `BrickTile` и источника выбранной темы. Затем переключите тему во время игры.

**Критерий готовности:** можете показать, почему рисунок изменился, а символ карты, возможность копания и восстановление Кирпича остались прежними.

Кнопки размеров выбирают 18, 32, 48 или 64 пикселя; анимацию и подсветку можно включать отдельно. На узком окне карточки переносятся, содержимое прокручивается.

Ниже расположен [`PlayerGallery.qml`](qml/examples/PlayerGallery.qml): четыре варианта Персонажа, состояния `idle/run/climb/dig/fall` и переключение направления. Общие размер и разрешение анимации передаются из окна галереи; подсветка относится к тайлам.

### Этап C — изучить контракт компонентов тайлов

[`GameTile.qml`](qml/components/tiles/GameTile.qml) задаёт общий размер, выбор темы, изображение, подсветку и анимацию. `BrickTile`, `CrystalTile`, `PrizeTile` задают тип представления и геометрический вариант Classic.

| Свойство | По умолчанию | Назначение |
|---|---|---|
| `cellSize` | `32` | Ширина и высота компонента |
| `theme` | `"classic"` | `classic`, `kenney`, `industrial`; неизвестное значение использует Classic |
| `highlighted` | `false` | Зелёная рамка |
| `animated` | `true` | Пульсация спрайта обычного Приза; `false` фиксирует его непрозрачность |
| `crystalColor` | `"#35d6c4"` | Только `CrystalTile`: цвет геометрического кристалла Classic |

Например, из `qml/main.qml`:

```qml
import "components/tiles" as Tiles

Tiles.BrickTile {
    cellSize: 32
    theme: "kenney"
    animated: false
}
```

Не передавайте сюда столкновения, очки или таймер восстановления клетки. Визуальный компонент должен работать в галерее без движка и конкретного уровня.

**Критерий готовности:** можете создать компонент в отдельном экране и объяснить каждое передаваемое свойство.

### Этап D — разобраться с темами

[`TileTheme.qml`](qml/components/tiles/TileTheme.qml) — базовый объект с `name`, `brickSource`, `crystalSource`, `prizeSource`. `ClassicTheme` оставляет источники пустыми: специализированные тайлы рисуют геометрию. `KenneyTheme` и `IndustrialTheme` задают URL PNG.

`GameTile` выбирает объект темы по строке `theme`, затем источник по типу тайла. `usesSprite` определяет, показывать ли изображение или геометрическую отрисовку. Загрузка проверяется через `imageStatus`.

**Задание:** найдите, какие места придётся расширить для четвёртой темы Blocks: объект темы, выбор в `GameTile`, игровой переключатель, список галереи, ресурсы и тесты. Составьте список до изменения кода, чтобы не получить тему, доступную только в одном экране.

**Критерий готовности:** смена темы обновляет источники всех трёх тайлов и не меняет их семантический тип.

### Этап E — проследить подключение к игре

[`Tile.qml`](qml/components/Tile.qml) выбирает `sourceComponent` через `Loader`: `brick` → `BrickTile`, `crystal` → `CrystalTile`, `gold` → `PrizeTile`. Для других типов этот Loader пуст; Сейф, Ключ, выход и специальные Призы сохраняют прежнюю отрисовку. Пустая и выкопанная клетки не получают изображение Кирпича.

Координаты делегата задаёт `Repeater` в `main.qml`; `Tile.qml` передаёт размер, тему и визуальные свойства выбранному компоненту. Единственный выбор темы игрового поля — `root.tileTheme`. Кнопка «Тема» циклически переключает `classic → kenney → industrial`.

**Критерий готовности:** можете отдельно проследить расположение клетки, выбор её представления и передачу цвета кристалла Classic, не меняя C++.

## 7. Варианты Персонажа

У героя есть независимые характеристики: положение, действие, направление и внешний вид. Первые три поступают из движка; оформление выбирается в интерфейсе.

```qml
Player {
    size: root.tileSize
    variant: root.playerVariant
    x: gameEngine.playerX * root.tileSize
    y: gameEngine.playerY * root.tileSize
    state: gameEngine.playerState
    facingRight: gameEngine.playerFacingRight
}
```

Здесь `variant` не заменяет `state`: робот может бежать или копать так же, как космонавт. Не создавайте для каждого оформления отдельную копию логики движения.

### Каталог вариантов

[`PlayerStyles.qml`](qml/components/PlayerStyles.qml) содержит массив `variants`: ключ, подпись и номера кадров. `style(key)` возвращает описание или классический вид для неизвестного ключа. `next(key)` выбирает следующий вариант для кнопки «Герой».

| Ключ | Вид | Кадры в `pixel-platformer/Tiles/Characters/` |
|---|---|---|
| `classic` | Классический зелёный Персонаж из фигур QML | PNG не используются |
| `astronaut` | Зелёный космонавт | `tile_0000.png`, `tile_0001.png` |
| `pink` | Розовый космонавт | `tile_0004.png`, `tile_0005.png` |
| `robot` | Робот | `tile_0018.png`, `tile_0019.png`, `tile_0020.png` |

Все выбранные PNG Персонажей имеют размер 24×24 и лицензию CC0. Источник и лицензия описаны в [каталоге Kenney](assets/tilesets/kenney/README.md).

### Контракт Player.qml

| Свойство | По умолчанию | Назначение |
|---|---|---|
| `size` | `32` | Ширина и высота компонента |
| `variant` | `"classic"` | Ключ оформления из `PlayerStyles` |
| `state` | `"idle"` | `idle`, `run`, `climb`, `dig`, `fall` из движка |
| `facingRight` | `true` | Направление взгляда |
| `animated` | `true` | Разрешение перебора кадров |

`selectedStyle`, `spriteSource`, `usesSprite` и `imageStatus` вычисляются из этих свойств и используются при отрисовке и проверках.

### Как работает анимация

В [`Player.qml`](qml/components/Player.qml) используется `Image` и `Timer`, а не `SpriteSequence`. Таймер с интервалом 140 мс перебирает выбранные кадры, если Персонаж видим, использует спрайты, анимация разрешена и состояние равно `run`, `climb` или `dig`.

В `idle` и `fall` выбирается первый кадр. Изменение состояния, варианта или флага `animated` сбрасывает индекс кадра. Зеркальное отражение задаётся выражением `mirror: !player.facingRight`. Копание обозначается наклоном ±12°, падение — ±6°. Наклон сохраняется при `animated: false`, поскольку зависит от состояния, а не от таймера.

Имеющиеся кадры используются для нескольких действий. Отдельных последовательностей для бега, лазания и копания в текущем варианте нет. Классический Персонаж остаётся геометрическим: при копании меняет цвет на оранжевый, направление показывает глаз.

Таймер меняет только индекс визуального кадра. Он не вызывает `movePlayer`, не начисляет очки и не изменяет игровую карту.

### Упражнение 5.5 — проследить выбор героя

1. Найдите `root.playerVariant` и кнопку с `objectName: "playerVariantButton"` в `main.qml`.
2. Проследите вызов `playerStyles.next(...)`, обновление `Player.variant`, вычисление `selectedStyle` и `spriteSource`.
3. Во время движения переключите оформление и проверьте направление и позицию.
4. Найдите в `test_tilelibrary.cpp` проверку реальных нажатий кнопки и сохранения значений движка.

**Критерий готовности:** можете объяснить, как смена PNG обновляет изображение без изменения состояния `GameEngine`.

### Упражнение 5.6 — добавить собственный вариант

Выберите другую пару кадров из `Tiles/Characters/`, проверьте их визуально и добавьте описание в `PlayerStyles.variants`. Включите PNG в `qml.qrc`, обновите каталог лицензий и набор данных теста `playerVariants_data()`.

Игровой переключатель и галерея Персонажей читают общий каталог, поэтому для обычного нового варианта отдельные кнопки или условия в них не нужны. Расширение способа отрисовки, например добавление отдельных кадров для каждого действия, потребует изменения контракта каталога и `Player.qml`.

**Критерий готовности:** новый герой появляется в игре и галерее, оба направления работают, кадры загружаются, существующие варианты проходят тесты.

### Управление оформлением в игре

- «Тема» меняет только оформление Кирпича, Кристалла и обычного Приза.
- «Герой» переключает четыре варианта Персонажа независимо от темы тайлов.
- «Галерея тайлов» открывает сравнение тайлов и Персонажей; нижняя часть доступна прокруткой.

Выбор темы и героя не сохраняется между запусками: игра начинает с `classic`. Галерея использует собственное состояние предпросмотра и не выбирает героя за игрока.

На H2 зависимости распакованы в `/home/majorov/.local/share/qml-build-deps/root`. Локальные `env.sh` и `run.sh` находятся в игнорируемом каталоге сборки; они не входят в репозиторий и после удаления каталога не восстанавливаются автоматически.

### Что проверяется автоматически

| Группа CTest | Проверки |
|---|---|
| `gameengine` | Существующие тесты игровых правил и состояния движка |
| `tilelibrary` | Три компонента тайлов × три темы × размеры 18/32/64; загрузка изображений и смена темы существующего экземпляра |
| `tilelibrary` | Четыре варианта Персонажа × пять состояний × два направления × размеры 32/64; возврат к Classic для неизвестного ключа |
| `tilelibrary` | Смена кадров робота и остановка анимации |
| `tilelibrary` | Загрузка и изменение размеров галереи без экземпляра GameEngine |
| `tilelibrary` | Смена темы и нажатия кнопки «Герой» в игровом окне без изменения позиции, счёта и числа Призов; сохранение привязок действия и направления Персонажа |

QML-проверки находятся в [`tests/test_tilelibrary.cpp`](tests/test_tilelibrary.cpp), отслеживают предупреждения через `QQmlEngine::warnings` и запускаются CTest без видимого окна с `QT_QPA_PLATFORM=offscreen`, `QT_QUICK_BACKEND=software`. Перед использованием `QSignalSpy` тип `QList<QQmlError>` регистрируется через `qRegisterMetaType`, чтобы параметры сигнала можно было прочитать.

Необязательный снимок галереи на H2:


При указанной переменной тест увеличивает окно до 960×1040 и сохраняет изображение через `contentItem()->grabToImage()`. Оно включает тайлы и Персонажей. Снимок находится в `/home/majorov/docs/QML-tile-gallery.png` и не входит в репозиторий.

### Финальная ручная проверка

1. Запустите галерею, сравните три темы и четыре варианта героя при разных размерах.
2. Включите анимацию, проверьте состояния и оба направления взгляда.

6. Просмотрите консоль на ошибки ресурсов, неизвестные свойства и нарушения привязок.

Сборка и обе группы автоматических тестов прошли при реализации. Галерея проверена по снимку. Полное ручное прохождение игровых сценариев после смены графики остаётся отдельной проверкой.

## Что дальше

Можно добавить новый вариант героя по упражнению 5.6, четвёртую тему Blocks или отдельные наборы кадров для каждого действия. Сохранение выбранного оформления между запусками и упаковка файловой библиотеки как QML-модуля — следующие самостоятельные задачи.

При расширении сохраняйте направление потока: ввод QML → команда движку → изменение состояния и модели → уведомление → обновление интерфейса. Выбор оформления действует только на последнее звено.
