# LEARNING_05.md — библиотека игровых тайлов на QML

Это продолжение курса после [`LEARNING_04.md`](LEARNING_04.md). Практический проект — создать собственную библиотеку визуальных компонентов игровых тайлов, собрать галерею вариантов оформления и подключить выбранный стиль к Boulder Dash. По пути разбирается полный путь изменения: действие игрока вызывает метод `GameEngine`, движок меняет данные, модель посылает уведомление, а QML обновляет тайл, Персонажа или HUD.

## Цель

Научиться находить ошибки на границе C++ и QML и создавать повторно используемые QML-компоненты. Если очки изменились в C++, но не обновился HUD, проблема обычно в уведомлении свойства. Если изменился символ карты, но картинка осталась прежней, проверьте модель и её сигнал `dataChanged`. Если Персонаж визуально не движется, проверьте привязки `x`, `y` и `playerPositionChanged`.

В проекте есть два разных канала обновления интерфейса:

1. **Свойства `GameEngine`.** Например, `score`, `playerX`, `hasKey`. QML читает их как `gameEngine.score`; после изменения C++ должен испустить указанный в `Q_PROPERTY` сигнал `NOTIFY`.
2. **Модели списков.** `tilesModel` и `enemiesModel` — объекты `QAbstractListModel`. QML получает их роли через `Repeater`; изменение одной записи модели должно сообщить об этом через `dataChanged`, а полная замена списка — через `beginResetModel()` / `endResetModel()`.

Оба канала описывают отображение состояния. Источником игровых правил остаётся C++-движок; не создавайте в QML вторую независимую копию карты или счёта.

## 1. Проследите движение Персонажа

Начните с нажатия клавиши:

```text
Keys.onPressed в qml/main.qml
  → gameEngine.movePlayer(dx, dy)
  → изменение m_playerX и m_playerY в src/gameengine.cpp
  → emit playerPositionChanged()
  → обновление x и y компонента Player в qml/main.qml
```

Метод доступен QML благодаря `Q_INVOKABLE`. Свойства `playerX` и `playerY` объявлены через `Q_PROPERTY` с `NOTIFY playerPositionChanged`. Компонент `Player.qml` не знает правил столкновения: его координаты привязаны к свойствам движка.

Привязка QML выглядит так:

```qml
Player {
    x: gameEngine.playerX * root.tileSize
    y: gameEngine.playerY * root.tileSize
    state: gameEngine.playerState
    facingRight: gameEngine.playerFacingRight
}
```

Если после хода значение `playerX` изменилось, но спрайт стоит, проверьте правильность `NOTIFY` сигнала и отсутствие императивного присваивания `player.x` в другом месте. Такое присваивание может разорвать декларативную привязку.

### Упражнение 5.1 — проследить одно действие

Выберите ход Персонажа и найдите его путь в коде от нажатой клавиши до изображения. Запишите файлы, функции и сигнал в порядке вызова.

**Критерий готовности:** можете объяснить, почему ход блокируется, где меняются координаты и какое уведомление заставляет QML переместить компонент.

## 2. Проследите изменение клетки

Карта хранится в `GameEngine::m_grid`, а визуальные типы клеток — в `TileModel`. Например, при копании символ Кирпича `#` заменяется на `.`; модель обновляется типом `dug`. При восстановлении символ снова становится `#`, а тип модели — `brick`.

В `TileModel` определены роли:

```cpp
enum Roles { RowRole = Qt::UserRole + 1, ColRole, TypeRole };

QHash<int, QByteArray> roleNames() const override {
    return {
        {RowRole, "row"},
        {ColRole, "col"},
        {TypeRole, "type"}
    };
}
```

`roleNames()` задаёт имена, которые видит QML. `Repeater` создаёт для каждой записи `Tile`, координаты и вид которого читаются из ролей:

```qml
Repeater {
    model: gameEngine.tilesModel
    delegate: Tile {
        x: model.col * root.tileSize
        y: model.row * root.tileSize
        type: model.type
    }
}
```

Метод `TileModel::updateTile()` меняет тип записи и испускает `dataChanged` для роли `TypeRole`. Если поменять `m_grid`, но забыть обновить модель, физика и картинка разойдутся. Если обновить только модель, а не `m_grid`, игрок увидит один объект, а правила столкновения будут считать другой.

### Упражнение 5.2 — проверить уведомление модели

1. Найдите путь копания от `GameEngine::dig()` до `TileModel::updateTile()`.
2. Найдите путь восстановления Кирпича из `startDugTileTimer()`.
3. Проверьте в `Tile.qml`, как типы `brick` и `dug` влияют на отрисовку.
4. В тесте наблюдайте `dataChanged` через `QSignalSpy` и проверьте, что при изменении типа модели приходит одно уведомление.

**Критерий готовности:** тест различает изменение внутренней карты и уведомление визуальной модели; после копания и восстановления вид тайла соответствует игровому правилу.

## 3. Свойства и сигнал `NOTIFY`

`Q_PROPERTY` описывает мост между C++-значением и QML:

```cpp
Q_PROPERTY(int score READ score NOTIFY scoreChanged)
```

`READ score` сообщает, как прочитать значение. `NOTIFY scoreChanged` сообщает QML, когда перечитать его. Сигнал не заменяет значение: сначала движок изменяет поле, затем испускает уведомление.

В HUD используется декларативное выражение:

```qml
text: qsTr("Очки: %1").arg(gameEngine.score)
```

При сборе Приза движок добавляет очки и испускает `scoreChanged`; QML сам пересчитывает текст. Не присваивайте текст HUD вручную после каждого действия: это дублирует реактивную связь.

У одного сигнала может быть несколько связанных свойств. Например, `scoreChanged` используется для счёта, рекорда, жизней и оставшихся Призов. Когда добавляете свойство или меняете существующее, проверьте, что сигнал испускается во всех путях изменения значения: копание, таймер, сбор награды, перезапуск и смена уровня.

### Упражнение 5.3 — найти пропущенное уведомление

Выберите одно `Q_PROPERTY` в `gameengine.h`. Найдите все места, где соответствующее поле меняется, и проверьте, что каждое изменение сопровождается нужным сигналом. Добавьте или расширьте тест с `QSignalSpy` для наиболее важного сценария.

**Критерий готовности:** значение и сигнал проверяются отдельно: тест подтверждает новое значение и ожидаемое число уведомлений.

## 4. Виджет QML не должен владеть правилами игры

`Tile.qml` отвечает за внешний вид тайла: цвет, рамку, символ или анимацию. `GameEngine` отвечает за то, можно ли войти в клетку, начисляются ли очки и когда таймер восстанавливает Кирпич. Например, `dug` отображается как пустая клетка, но проходимость определяется картой движка, а не цветом делегата.

Полезное разделение вопросов:

| Наблюдение | Где искать причину |
|---|---|
| Персонаж не может войти в клетку | `playerCanEnter()` и символ в `m_grid`. |
| Игрок вошёл, но картинка клетки старая | `TileModel::updateTile()` и `dataChanged`. |
| Счёт изменился в C++, но не в HUD | `Q_PROPERTY`, `NOTIFY` и `scoreChanged`. |
| Вид тайла неверный, но модель содержит правильный тип | `Tile.qml`, свойство `type` и условие `visible`. |
| Уровень изменился, но размер игрового поля старый | свойства `rows`/`columns` и `levelChanged`. |

## 5. Порядок диагностики

Когда визуальный результат не соответствует ожиданиям, проверяйте слои по порядку:

1. **Ввод:** получил ли `gameRoot` клавиатурное событие? У него должны быть `focus: true` и подходящий обработчик.
2. **Вызов:** был ли вызван нужный `Q_INVOKABLE` метод?
3. **Правило:** разрешают ли игровые данные действие? Проверьте координаты, символ клетки и условие столкновения.
4. **Состояние:** изменилось ли значение в `GameEngine` или `m_grid`?
5. **Уведомление:** испущен ли `NOTIFY` сигнал либо сигнал модели `dataChanged`?
6. **Представление:** получает ли QML правильное свойство/роль и рисует ли `Tile.qml` соответствующий тип?

Такой порядок отделяет «ход запрещён игровым правилом» от «ход состоялся, но интерфейс не обновился». Не исправляйте картинку, пока не выяснили, какое состояние хранит движок.

## 6. Ручная проверка интерфейса

Qt Test проверяет значения и сигналы, но не заменяет визуальный запуск. После изменений QML вручную проверьте:

- ход в каждую сторону и поворот Персонажа;
- копание, вход в яму, выход и восстановление Кирпича;
- обновление очков, Призов, жизней и Ключа в HUD;
- уведомления о Ключе, Сейфе и конце игры;
- разные размеры окна и отсутствие обрезания текста или тайлов.

Проверьте вывод приложения на сообщения `QML` об ошибках привязки, неизвестных свойствах и типах. Ошибка в консоли часто указывает на неверное имя роли или свойства ещё до ручного поиска по экрану.

## Практический проект — своя библиотека игровых тайлов

В проект уже скачаны три графических набора Kenney: [Pixel Platformer](assets/tilesets/kenney/README.md), Blocks и Industrial Expansion. В них PNG-изображения, а не готовые QML-классы. Это хороший материал, чтобы научиться строить свои компоненты поверх чужих лицензированных ресурсов.

### Этап A — составить каталог тайлов

Откройте `Preview.png` каждого набора и выберите изображения для Кирпича, Кристалла и Приза. Проверьте отдельные изображения в `Tiles/` и таблицу `Tilesheet*.txt`. Запишите для каждого выбранного PNG: тип объекта, имя файла, размер, источник и лицензию. Не выбирайте спрайт только по имени файла: визуально проверьте прозрачный фон, границы и масштаб.

Размер сетки наборов — 18×18 пикселей, размер клетки проекта — 32×32. Масштабирование в QML должно сохранять пропорции и резкие пиксельные границы; для пиксельной графики установите `smooth: false`. Попробуйте отрисовку одного PNG в 32×32 и проверьте, не обрезаны ли края.

**Критерий готовности:** составлена таблица выбранных файлов; изображения можно различить в клетке размера проекта и они не содержат фон превью.

### Тип объекта и его представление — разные данные

Символы уровней (`#`, `C`, `$` и другие) остаются в карте и задают игровые правила. При загрузке движок преобразует их в семантические типы модели (`brick`, `crystal`, `gold` и т. п.). QML получает этот тип и отображает подходящий компонент или спрайт. Выбор графики не должен менять тип клетки в `m_grid`, ASCII-карту или физику.

Например, делегат может передавать тип и тему отдельно:

```qml
Tile {
    type: model.type       // "brick", "crystal", "gold"
    theme: root.tileTheme  // "classic", "kenney", "industrial"
}
```

Для выбора между несколькими темами используйте строковое свойство или перечисление, а не булевый флаг: флаг удобно выражает только два варианта, тогда как тема может иметь три и больше значения. Изменение `tileTheme` по привязке обновит все делегаты, не затрагивая данные уровня.

Флаги подходят для временных визуальных состояний, например `highlighted` или `animated`. Свойство `visualVariant` для конкретной клетки добавляйте только тогда, когда ей действительно нужен отдельный рисунок в рамках одной темы. Не храните в таком свойстве информацию, которая уже выражена типом объекта или игровым состоянием.

### Упражнение 5.4 — проследить представление объекта

Возьмите Кирпич из карты: проследите путь от `#` до типа `brick` в модели и до QML-компонента, который его рисует. Затем выберите для него другую тему.

**Критерий готовности:** при смене темы меняется изображение Кирпича, но его символ карты и поведение при копании остаются прежними.

### Этап B — сделать галерею для быстрого просмотра

Создайте отдельный экран `qml/examples/TileGallery.qml`, который не использует `GameEngine`. Разместите на сетке несколько вариантов Кирпича, Кристалла и Приза, подпишите стиль и имя файла. Галерея помогает сравнить наборы без перезапуска игры и не затрагивает реальные уровни.

Минимальный пример отображения изображения:

```qml
Image {
    width: 32
    height: 32
    source: "../../assets/tilesets/kenney/pixel-platformer/Tiles/tile_0000.png"
    fillMode: Image.PreserveAspectFit
    smooth: false
}
```

Путь к выбранному файлу нужно подставить после просмотра каталога. Если приложение загружает QML из ресурсов `qrc:/`, добавьте галерею и нужные PNG в `qml.qrc`; пути ресурсов должны соответствовать alias в `.qrc`. Для первого эксперимента галерею можно запускать отдельно с `qmlscene`, если он установлен для используемого Qt.

**Критерий готовности:** одна галерея показывает несколько наборов рядом и позволяет увидеть масштабирование и прозрачность.

### Этап C — определить контракт компонентов

Перед созданием файлов решите, какие общие свойства получают компоненты. Начните с небольшого API:

| Свойство | Назначение |
|---|---|
| `cellSize` | Ширина и высота компонента на игровом поле. |
| `theme` | Выбранный набор оформления. |
| `highlighted` | Необязательная подсветка для отладки или эффектов. |
| `animated` | Разрешение анимации; позволяет выключать её в галерее и тестовых снимках. |

Создайте `GameTile.qml` для общего контейнера и поведения изображения, затем специализированные `BrickTile.qml`, `CrystalTile.qml` и `PrizeTile.qml`. У каждого компонента должен быть один понятный контракт. Не добавляйте сюда координаты физической карты, столкновения, очки или таймер восстановления — это не визуальные обязанности тайла.

Компонент должен корректно работать в нескольких размерах, не менять игровые данные и не требовать конкретного уровня. Это и делает его пригодным для повторного использования в другом экране или приложении.

**Критерий готовности:** можно создать по одному экземпляру каждого тайла в галерее, задав им размер и стиль через свойства.

### Этап D — добавить темы оформления

Сначала сделайте два стиля: существующий геометрический и один выбранный набор Kenney. Затем добавьте Industrial Expansion как третий. Например, заведите `TileTheme.qml` с URL спрайтов Кирпича, Кристалла и Приза, а конкретные темы реализуйте отдельными компонентами (`ClassicTheme.qml`, `KenneyTheme.qml`, `IndustrialTheme.qml`). Выбор темы должен менять источники изображений, но не `type` и не игровые правила.

Для начала допустима простая проверка `theme.name` в QML-компоненте. Если условные выражения разрастаются, перенесите таблицу источников в отдельный объект темы. Не создавайте C++-плагин ради обычных картинок: эта библиотека состоит из QML и ресурсов.

**Критерий готовности:** переключение темы в галерее меняет вид Кирпича, Кристалла и Приза, не меняя подписи объектов или состояние движка.

### Этап E — подключить семейство к игровому полю

Постепенно разделите текущий [`Tile.qml`](qml/components/Tile.qml): оставьте в нём координаты, размер клетки и передачу состояния, а рисование Кирпича, Кристалла и Приза перенесите в новые компоненты. Начните с одного типа и после ручной проверки переносите следующий. Сейф, Ключ, выход и яма могут пока оставаться в старом компоненте.

`Tile.qml` получает визуальный `type` и вспомогательные свойства из модели и `GameEngine`, а затем передаёт их нужному QML-компоненту. Удобно применить `Loader` с `sourceComponent` или явные компоненты с условиями видимости. Какой вариант выбрать, сравните по читаемости и удобству отладки.

Измените стиль в одном месте, например свойством верхнего уровня `tileTheme`, и передайте его вниз. Не дублируйте переключатель в каждом тайле. Не меняйте символы карты (`#`, `C`, `$`) и физику ради внешнего вида.

**Критерий готовности:** при смене темы меняется только графика; копание, движение через яму, сбор Призов, падение Кристаллов, Ключ и Сейф ведут себя как прежде.

### Этап F — оформить библиотеку для повторного использования

Когда компоненты работают в игре, зафиксируйте API и структуру:

```text
qml/components/tiles/
  GameTile.qml
  BrickTile.qml
  CrystalTile.qml
  PrizeTile.qml
  TileTheme.qml
  ClassicTheme.qml
  KenneyTheme.qml
  IndustrialTheme.qml
```

Добавьте README с описанием публичных свойств, скриншотом галереи, способом подключения и ссылками на лицензии ресурсов. Для продвинутого варианта оформите каталог как QML-модуль с `qmldir` и версией импорта. Сначала завершите файловый вариант: модуль и установка в Qt import path — отдельная тема упаковки и развёртывания.

### Финальная проверка проекта

1. Запустите галерею и проверьте все три темы и их размеры.
2. Соберите игру и выполните `ctest --test-dir build-qt5 --output-on-failure`.
3. Запустите игру и пройдите вручную сценарии копания, падения Кристалла, сбора Приза, восстановления Кирпича и открытия Сейфа.
4. Проверьте QML-вывод на ошибки загрузки изображений, неизвестные свойства и разорванные привязки.
5. Сравните игровой экран до и после подключения: должны измениться только визуальные компоненты.

**Результат:** независимый набор QML-компонентов тайлов, три темы, галерея предварительного просмотра и документированная лицензия каждого набора графики.

## Что дальше

После этого этапа можно перейти к разбиению `GameEngine` на независимые компоненты, добавить отдельные QML/UI-тесты или заняться упаковкой библиотеки как QML-модуля. При каждом расширении сохраняйте одно направление потока: ввод QML → команда движку → изменение модели → уведомление → обновление интерфейса.
