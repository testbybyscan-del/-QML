## 1. Чему учит эта часть

По итогам практики вы должны уметь не только добавить условие в `if`, но и объяснить:

- где хранится истинное состояние игры и кто имеет право его менять;
- как изменение C++-свойства приводит к обновлению QML;
- почему `QAbstractListModel` требует `beginResetModel()`, `dataChanged()` и именованных ролей;
- как разделить координаты клетки и пиксельные координаты окна;
- как обновить игровую карту и модель отображения согласованно;
- как избежать повторного начисления за один и тот же приз;
- как сохранять изменённый экран при переходе на другой;
- как сделать движение объектов детерминированным и воспроизводимым;
- как находить и закрывать крайние случаи до того, как они превращаются в ошибки.

Уверенный middle — это не число выученных классов Qt. Это способность взять неоднозначную задачу, уточнить поведение, разделить её на маленькие изменения, защитить инварианты, проверить результат и понятно объяснить компромиссы.

## 2. Карта проекта и путь данных

Основные файлы игры:

| Файл | Роль |
|---|---|
| `main.cpp` | Создаёт Qt-приложение и загружает корневой QML-компонент. |
| `src/gameengine.h` | Объявляет игровой движок, свойства, сигналы, модели и внутреннее состояние. |
| `src/gameengine.cpp` | Реализует карту, движение, сбор предметов, переходы, таймеры и симуляцию. |
| `qml/main.qml` | Окно игры, клавиатурный ввод, игровой таймер, HUD и сборка экрана. |
| `qml/components/Tile.qml` | Рисует один тип клетки. |
| `qml/components/Player.qml` | Рисует игрока и выбирает его визуальное состояние. |
| `qml/components/Enemy.qml` | Визуальный компонент врага, если он включён в текущую сцену. |
| `CMakeLists.txt`, `qml.qrc` | Настраивают сборку и включение QML-ресурсов. |

Путь команды движения выглядит так:

```text
нажатие клавиши
    ↓
Keys.onPressed в qml/main.qml
    ↓
gameEngine.movePlayer(dx, dy)
    ↓
проверка границ и коллизий в C++
    ↓
изменение m_grid, координат и счёта
    ↓
emit playerPositionChanged()/scoreChanged()
    ↓
QML-привязки перечитывают свойства и перерисовывают экран
```

Такое разделение обычно удобно для игры на сетке: C++ решает, **что произошло**, QML отвечает за то, **как это выглядит и как пользователь подаёт команды**. Важно: не создавайте две независимые версии истины. Если позиция игрока хранится и в C++, и отдельной переменной в QML, рано или поздно они разойдутся.

## 3. Шаг 1. Игровой мир как сетка

Для игры с клетками удобно хранить мир в строках. В текущей реализации символ в `m_grid[row][col]` кодирует тип клетки или сущность:

```cpp
// Пример легенды карты:
// '#' — кирпич, '.' — пусто, 'C' — кристалл,
// '$' — приз, 'P' — начальная позиция игрока.
static const QVector<QString> level = {
    "########",
    "#..$...#",
    "#..C...#",
    "#..P...#",
    "########"
};
```

`row` — номер строки, `col` — номер столбца. В C++ обращение к символу выглядит как `m_grid[row][col]`. Для экрана из 20 колонок и клетки размером 32 пикселя преобразование координат такое:

```qml
x: col * tileSize
y: row * tileSize
```

Например, клетка `(col: 3, row: 2)` занимает пиксельную позицию `(96, 64)`, если `tileSize` равен 32. Логика игры должна работать в клетках; умножение на размер клетки относится к отображению.

### Границы — часть модели, а не только картинки

У `tileAt()` полезно задать безопасное поведение для координат за картой. Например, считать их стеной:

```cpp
QChar GameEngine::tileAt(int row, int col) const
{
    // За пределами уровня персонаж и физические объекты упираются в стену.
    if (row < 0 || row >= m_rows || col < 0 || col >= m_columns)
        return '#';

    return m_grid[row][col];
}
```

Так уменьшается количество проверок индексов у каждого вызывающего кода. Это решение нужно применять осознанно: если где-то выход за границу должен означать ошибку или пустоту, используйте отдельную проверку вместо скрытой подмены.

### Разделяйте чтение и запись

`tileAt()` читает клетку, `setTileAt()` меняет символ. Это помогает централизовать проверку координат и позже добавить журналирование или дополнительную логику.

```cpp
void GameEngine::setTileAt(int row, int col, QChar value)
{
    if (row < 0 || row >= m_rows || col < 0 || col >= m_columns)
        return;

    m_grid[row][col] = value;
}
```

Однако `setTileAt()` сам по себе не обновляет QML-модель. Это важный архитектурный вопрос, к которому вернёмся: симуляция и представление обязаны оставаться синхронными.

### Упражнение 3.1 — карта и инварианты

1. Выпишите допустимые символы текущей карты.
2. Для каждого символа укажите смысл и то, можно ли войти в такую клетку.
3. Проверьте, что каждая строка уровня имеет одинаковую длину.
4. Найдите старт `P`, посчитайте все `$`.
5. Продумайте, что должно произойти, если карты нет, строка короче ожидаемой или стартовая позиция отсутствует.

**Инварианты** — условия, которые должны оставаться верными всегда. Примеры: размеры сетки не меняются во время уровня; игрок всегда внутри карты; приз, уже собранный игроком, больше не лежит в клетке.

На первом этапе достаточно добавить проверку карты при загрузке. Не исправляйте данные молча: сообщите об ошибочной строке через `qWarning()` и решите, следует ли остановить загрузку уровня.

## 4. Шаг 2. Модель Qt и отображение QML

QML не должен получать случайный доступ к внутреннему `QVector` движка. Для списков объектов Qt предоставляет `QAbstractListModel`. Она сообщает представлению число строк, значения ролей и уведомляет, какие элементы изменились.

Упрощённый пример модели клеток:

```cpp
class TileModel : public QAbstractListModel
{
    Q_OBJECT
    QML_ELEMENT

public:
    // Роли — поля одной строки модели, доступные делегату QML.
    enum Roles { RowRole = Qt::UserRole + 1, ColRole, TypeRole };

    struct Tile {
        int row;
        int col;
        QString type;
    };

    int rowCount(const QModelIndex &parent = {}) const override
    {
        // Плоская модель не имеет дочерних строк.
        return parent.isValid() ? 0 : m_tiles.size();
    }

    QVariant data(const QModelIndex &index, int role) const override
    {
        if (!index.isValid() || index.row() < 0 || index.row() >= m_tiles.size())
            return {};

        const Tile &tile = m_tiles.at(index.row());
        switch (role) {
        case RowRole:  return tile.row;
        case ColRole:  return tile.col;
        case TypeRole: return tile.type;
        default:       return {};
        }
    }

    QHash<int, QByteArray> roleNames() const override
    {
        // Эти имена превращаются в свойства делегата QML.
        return {
            { RowRole, "row" },
            { ColRole, "col" },
            { TypeRole, "type" }
        };
    }

private:
    QVector<Tile> m_tiles;
};
```

Каждое поле строки доступно делегату под именем роли. В QML `Repeater` создаёт делегат на каждую запись:

```qml
Repeater {
    model: gameEngine.tilesModel

    delegate: Tile {
        x: model.col * root.tileSize
        y: model.row * root.tileSize
        size: root.tileSize
        type: model.type
    }
}
```

В разных версиях Qt и в разных контекстах делегата доступ к ролям может писаться как `model.type` либо как отдельное свойство `type`. Если QML не находит роль, проверьте точное сообщение движка и форму модели, не маскируйте ошибку дублированием значений.

### Правильные уведомления модели

Если меняется весь набор клеток, модель должна объявить полный сброс:

```cpp
void setTiles(const QVector<Tile> &tiles)
{
    beginResetModel();
    m_tiles = tiles;
    endResetModel();
}
```

Если поменялся только тип одной клетки, нужно сообщить об изменении соответствующей строки:

```cpp
emit dataChanged(index(i), index(i), {TypeRole});
```

Без уведомления C++-данные могут быть правильными, но QML продолжит показывать старое значение. И наоборот, широкое обновление всей модели на каждую клетку работает, но создаёт лишнюю работу и скрывает точный масштаб изменения.

### Упражнение 4.1 — сделайте смену уровня

Реализуйте самостоятельно метод заполнения модели клетками. Затем выполните сценарии:

- полная загрузка карты обновляет всё поле;
- сбор одного приза обновляет ровно одну клетку;
- перемещение одного кристалла обновляет исходную и целевую клетки.

Для каждой операции подумайте, какое уведомление модели точнее: сброс всей модели или `dataChanged()`.

## 5. Шаг 3. Путь команды игрока

QML отвечает за преобразование клавиши в игровую команду. Например:

```qml
Keys.onPressed: (event) => {
    switch (event.key) {
    case Qt.Key_Left:
    case Qt.Key_A:
        gameEngine.movePlayer(-1, 0)
        break
    case Qt.Key_Right:
    case Qt.Key_D:
        gameEngine.movePlayer(1, 0)
        break
    case Qt.Key_Space:
        gameEngine.dig()
        break
    default:
        return // неизвестная клавиша остаётся доступна другим обработчикам
    }

    event.accepted = true
}
```

C++-метод объявляется доступным QML с помощью `Q_INVOKABLE`:

```cpp
Q_INVOKABLE void movePlayer(int dx, int dy);
```

Смысл `dx` и `dy` — направление в клетках. Влево — `(-1, 0)`, вверх — `(0, -1)`. Метод игрового движка должен проверить команду и применить её атомарно: либо перемещение состоялось целиком, либо состояние осталось прежним.

Порядок внутри функции полезно продумывать до написания кода:

1. Заблокировать действие, если игра завершена.
2. Проверить, что команда допустима: обычно движется ровно на одну клетку, а не по диагонали.
3. Вычислить целевые координаты.
4. Проверить препятствия и особые случаи, например толкание.
5. Изменить игровую сетку при необходимости.
6. Изменить координаты игрока.
7. Обработать предмет на целевой клетке.
8. Обновить состояние анимации.
9. Испустить сигналы для изменённых данных.
10. Проверить условия перехода на другой экран.

### Пример проверки команды

```cpp
bool GameEngine::isValidStep(int dx, int dy) const
{
    // Разрешён один шаг по горизонтали ИЛИ вертикали.
    // Нулевой шаг и диагональное движение запрещены.
    const bool oneAxisOnly = (dx == 0) != (dy == 0);
    const bool oneCell = qAbs(dx) <= 1 && qAbs(dy) <= 1;
    return oneAxisOnly && oneCell;
}
```

Такую проверку удобно выполнить до индексирования карты. Она защищает публичную команду от некорректных аргументов независимо от того, кто её вызвал — клавиатура, кнопка QML или будущий тест.

### Коллизии

Спросите у требований игры, какие клетки проходимы. Не делайте одну проверку наугад для всех типов объектов. Например, кирпич и кристалл — препятствия, приз можно собрать, пустая клетка проходима. Это можно выразить функцией:

```cpp
bool GameEngine::playerCanEnter(int row, int col) const
{
    const QChar tile = tileAt(row, col);
    return tile != '#' && tile != 'C';
}
```

Но эта функция говорит только о геометрической проходимости. Враг, дверь, лестница или яма могут требовать отдельных правил. Хорошие имена функций отражают точный контракт: `playerCanEnter()` не должна незаметно собирать приз или менять счёт.

### Упражнение 5.1 — реализуйте перемещение по шагам

Добавьте или перепишите `movePlayer()` в следующем порядке:

- сначала отсекайте недопустимый ввод;
- вычисляйте `nextX` и `nextY`;
- отдельно проверяйте столкновение с границей;
- отдельно проверяйте тип клетки;
- только после всех проверок меняйте координаты.

Попробуйте намеренно передать `(2, 0)`, `(1, 1)`, `(0, 0)` и `(-1, 0)`. Первые три команды должны быть отвергнуты, последняя — принята при свободной клетке.

**Инженерный принцип:** сначала проверка условий, затем изменение состояния. Так меньше шансов оставить мир в наполовину изменённом состоянии.

## 6. Шаг 4. Свойства, сигналы и обновление интерфейса

`Q_PROPERTY` делает значение C++-объекта доступным QML. Сигнал `NOTIFY` сообщает, когда это значение изменилось:

```cpp
Q_PROPERTY(int score READ score NOTIFY scoreChanged)

int score() const { return m_score; }

signals:
    void scoreChanged();
```

В QML создаётся привязка:

```qml
Text {
    text: "Очки: " + gameEngine.score
}
```

QML запоминает зависимость `text → gameEngine.score`. Когда C++ испускает `scoreChanged()`, привязка вычисляется заново. Это декларативная реактивность: мы задаём отношение между данными и отображением, а не вручную ищем и меняем `Text`.

При сборе предмета порядок важен:

```cpp
if (tileAt(nextY, nextX) == '$') {
    setTileAt(nextY, nextX, '.');
    m_tilesModel.updateTile(nextY, nextX, "empty");
    m_score += 100;
    --m_prizesLeft;
    emit scoreChanged();
}
```

Изменяются три согласованных части состояния: символ карты, вид клетки и значения счёта. Если забыть любую, получится расхождение: приз будет нарисован, но повторно соберётся; либо исчезнет с экрана, но останется в логике.

### Сигналы должны отражать смысл

Например, `playerPositionChanged()` означает, что изменились координаты. `scoreChanged()` означает, что изменились счётчики, зависящие от награды. Не нужно испускать один общий сигнал после каждого действия, если потребителям важно знать, какие именно данные обновились.

С другой стороны, не создавайте сигнал на каждое поле без необходимости. Группируйте уведомления по смыслу и документируйте их семантику. Также учитывайте, что `NOTIFY` часто объявляют без аргумента, но сигнал с новым значением тоже допустим, если его сигнатура подходит свойству и связям.

Для каждого `Q_PROPERTY` в `gameengine.h` заполните таблицу:

| Свойство | Геттер | Сигнал | Где меняется | Кто читает в QML |
|---|---|---|---|---|
| `playerX` | `playerX()` | `playerPositionChanged()` | движение/падение | `Player.x` |
| `score` | `score()` | `scoreChanged()` | сбор приза | HUD |

## 7. Шаг 5. Переходы и сохранение состояния экранов

Если состояние уровня живёт только в текущей сетке `m_grid`, обычная загрузка следующего уровня уничтожит изменения предыдущего. Нужно определить, что означает «сохранить уровень».

Минимальный снимок может выглядеть так:

```cpp
struct LevelSnapshot {
    QVector<QString> grid;
    int playerX = 0;
    int playerY = 0;
    int prizesLeft = 0;
    bool levelComplete = false;
    bool valid = false;
};
```

`valid` различает два случая: уровень ещё не открывали и нужно взять исходную карту; уровень уже посещали и нужно восстановить снимок. Иначе пустое поле состояния можно ошибочно принять за сохранённый экран.

### Сохранить перед переключением

```cpp
void GameEngine::saveCurrentLevel()
{
    LevelSnapshot &snapshot = m_levelSnapshots[m_currentLevel - 1];

    snapshot.grid = m_grid;
    snapshot.playerX = m_playerX;
    snapshot.playerY = m_playerY;
    snapshot.prizesLeft = m_prizesLeft;
    snapshot.levelComplete = m_levelComplete;
    snapshot.valid = true;
}
```

Снимок хранит значения, а не указатели на текущие контейнеры. Это упрощает восстановление и не связывает снимок с временем жизни временных объектов.

### Восстановить или создать уровень

```cpp
const bool hasSnapshot = snapshot.valid;
m_grid = hasSnapshot ? snapshot.grid : originalLevel;

if (hasSnapshot) {
    m_playerX = snapshot.playerX;
    m_playerY = snapshot.playerY;
    m_prizesLeft = snapshot.prizesLeft;
    m_levelComplete = snapshot.levelComplete;
} else {
    // Первый вход: найдите стартовую точку и посчитайте призы.
}
```

Важно не смешивать восстановление и первичную загрузку. При восстановлении нельзя ещё раз считать собранные призы, иначе HUD покажет исходное число, а не оставшееся.

### Переход как отдельная операция

```cpp
void GameEngine::switchToLevel(int targetLevel)
{
    if (targetLevel < 1 || targetLevel > kLevels.size())
        return;
    if (targetLevel == m_currentLevel || m_gameOver)
        return;

    saveCurrentLevel();
    m_currentLevel = targetLevel;
    m_playerState = "idle";
    loadLevel();
}
```

Метод переключения защищает инварианты: нельзя выбрать несуществующий экран, повторно загрузить текущий или переключиться после поражения. Все места перехода должны использовать эту операцию, иначе один путь может случайно забыть сохранить состояние.

### Правило доступа к переходу

Для следующего экрана проверяется условие текущего уровня: например, `m_prizesLeft == 0`. Для предыдущего уровня могут действовать другие правила. Не зашивайте номер экрана в разрозненные условия вроде `if (currentLevel == 2)`: по мере добавления карт это становится хрупким.

До кода составьте таблицу переходов:

| Текущий экран | Положение игрока | Условие | Цель |
|---|---|---|---|
| Первый | нижний правый угол | собраны все призы | следующий |
| Второй и дальше | нижний левый угол | переход назад разрешён | предыдущий |
| Любой | нижний правый угол | все призы текущего собраны | следующий |

Таблица — это спецификация. Если поведение спорное, выясните его до реализации.

### Упражнение 7.1 — снимки и обратный переход

Проверьте такие сценарии на бумаге, затем вручную в игре:

1. убрать приз на первом экране;
2. перейти на второй;
3. вернуться на первый;
4. убедиться, что приз не появился снова;
5. снова перейти на второй;
6. убедиться, что персонаж и карта второго уровня восстановились.

Отдельно решите, сохраняется ли позиция персонажа перед переходом или его следует помещать в точку входа. Оба варианта допустимы, если поведение определено явно и одинаково реализовано во всех переходах.

### Снимок в памяти и сохранение на диск — разные задачи

Текущие `LevelSnapshot` в `QVector` живут только пока работает процесс. Это сохранение состояния при переключении экранов, но не постоянное сохранение между запусками. Для сохранения прогресса после закрытия игры потребуется формат и отдельная задача: версия файла, обработка повреждения, пути пользователя, атомарная запись и миграция старых данных.

## 8. Шаг 6. Пошаговая физика кристаллов

В игре `updateCrystals()` вызывается по таймеру. Каждый вызов пытается выполнить один допустимый ход. Это упрощённая дискретная физика: состояние мира меняется шагами, а не непрерывными формулами скорости и ускорения.

В QML:

```qml
Timer {
    interval: 250
    running: true
    repeat: true
    onTriggered: gameEngine.updateCrystals()
}
```

Четыре вызова в секунду означают приблизительно четыре шага симуляции в секунду. Для обучения это удобно: изменения можно видеть и анализировать. Но интервал таймера не гарантирует точного реального времени — загруженный процесс может задержать событие.

### Шаг 1. Определить, что считается объектом физики

Приз `$` и кристалл `C` оба могут падать. Удобно ввести маленькие функции-предикаты:

```cpp
const auto isGem = [this](int row, int col) {
    const QChar tile = tileAt(row, col);
    return tile == 'C' || tile == '$';
};
```

Предикат выражает правило в одном месте. Если позже добавится тяжёлый камень, можно будет разделить объекты по весу, не копируя проверки по всему методу.

### Шаг 2. Описать порядок обновления

Если проходить карту сверху вниз, объект может переместиться вниз, а затем обработаться второй раз в том же тике. Часто для падающих предметов строки обходят снизу вверх:

```cpp
for (int row = m_rows - 2; row >= 1; --row) {
    for (int col = 1; col < m_columns - 1; ++col) {
        // Решение о перемещении клетки (row, col).
    }
}
```

Порядок обхода — часть поведения симуляции. Его нужно понимать и проверять, а не считать технической мелочью.

### Шаг 3. Найти цепочку

Вертикальная цепь — последовательные кристаллы или призы в одном столбце:

```cpp
int chainTop = row;
while (chainTop > 1 && isGem(chainTop - 1, col))
    --chainTop;
```

Если нижняя клетка цепочки свободна, всю цепь можно передвинуть вниз начиная с нижнего элемента, чтобы не затереть ещё не перемещённые данные:

```cpp
for (int sourceRow = row; sourceRow >= chainTop; --sourceRow) {
    const int destinationRow = sourceRow + 1;
    const QChar object = tileAt(sourceRow, col);

    setTileAt(destinationRow, col, object);
    setTileAt(sourceRow, col, '.');

    // Здесь же обновите визуальную модель обеих клеток.
}
```

Если копировать сверху вниз, сначала можно затереть значение клетки, которое ещё нужно прочитать. Направление копирования выбирается по зависимости данных.

### Шаг 4. Задать правило опоры и перекатывания

Перед реализацией запишите правила словами и таблицей решений. Например:

| Условие | Действие |
|---|---|
| Под объектом пусто и боковые клетки пусты | объект падает вниз |
| Под объектом другой кристалл, сбоку есть две свободные клетки | нижний объект перекатывается в сторону |
| Под объектом кирпич или объект упирается | остаётся на месте |
| Под цепью пусто | определить, должна ли переместиться вся цепь или отдельный объект |

Уточните, входит ли игрок в понятие «свободной клетки». Если игрок занимает клетку, симуляция может либо считать клетку занятой, либо разрешить падение и обрабатывать столкновение. Это уже игровое правило, а не деталь C++.

### Шаг 5. Перемещать атомарно

Сначала вычислите, какой ход будет сделан. Затем освободите исходные клетки и заполните целевые. Для сложного движения можно описать его через список перемещений:

```cpp
struct Move {
    int fromRow;
    int fromCol;
    int toRow;
    int toCol;
    QChar object;
};
```

План перемещения позволяет проверить все препятствия до изменения сетки. Это полезно, когда одной командой двигается цепочка из нескольких объектов.

### Шаг 6. Не забыть отображение

Изменение `m_grid` не обновляет `TileModel` само собой. Для движения объекта нужно обновить его исходную и конечную клетки. Если ход затронул цепь — каждую изменённую клетку. Проверьте инвариант после каждого тика:

> Каждому игровому объекту в сетке соответствует ровно одна видимая клетка того же типа в модели, и наоборот.

### Упражнение 8.1 — визуализируйте один тик на бумаге

Возьмите небольшую карту 7×6 с двумя кристаллами, кирпичом и пустым местом. Нарисуйте состояние до одного вызова `updateCrystals()`, затем вручную примените правила. Повторите для:

Проверьте и опишите:

## 9. Шаг 7. Время, таймеры и ямы

Для каждого вырытого блока в проекте создаётся `QTimer`, который через заданное время восстанавливает кирпич. Схема одноразового таймера:

```cpp
auto *timer = new QTimer(this); // QObject-владелец удалит таймер вместе с движком
timer->setSingleShot(true);

connect(timer, &QTimer::timeout, this, [this, row, col, timer]() {
    // Перед восстановлением проверьте текущее состояние клетки:
    // объект мог успеть занять её после копания.
    if (tileAt(row, col) == '.') {
        setTileAt(row, col, '#');
        m_tilesModel.updateTile(row, col, "brick");
    }

    timer->deleteLater();
});

timer->start(15000);
```

`this` как родитель задаёт владение по дереву `QObject`. Лямбда захватывает координаты и указатель таймера; захватывать нужно только значения, используемые внутри обработчика. Нельзя разыменовывать таймер после удаления.

### Срок жизни и повторное копание

Продумайте, что происходит, если одну клетку выкопали повторно до завершения старого таймера. Если оба таймера работают, первый может восстановить кирпич раньше нового срока. Возможные решения:

1. не создавать второй таймер для той же клетки;
2. остановить и перезапустить существующий таймер;
3. хранить время восстановления и проверять его в общем игровом цикле;
4. использовать поколение/идентификатор операции, чтобы старый обработчик не менял новое состояние.

Выбор зависит от требований. Не добавляйте сложную схему до появления реального сценария, но понимайте риск.

### Упражнение 9.1 — временная диаграмма

Для клетки нарисуйте шкалу: `t=0` — выкопали, `t=10` — повторно выкопали, `t=15` — сработал первый таймер, `t=25` — второй. Запишите ожидаемое поведение и проверьте, соответствует ли ему код.

Также проверьте переход на другой экран, пока таймер ещё работает. Старый таймер не должен случайно изменить модель нового уровня в тех же координатах. Поэтому при смене уровня таймеры останавливаются и удаляются/откладываются на удаление.

## 10. Шаг 8. Разделение симуляции и представления

На раннем этапе допустимо менять карту и `TileModel` рядом. С ростом проекта это создаёт риск забыть одно из двух. Рассмотрите улучшение: единая функция меняет игровую клетку и обновляет соответствующую роль модели.

Например:

```cpp
void GameEngine::changeTile(int row, int col, QChar value)
{
    if (row < 0 || row >= m_rows || col < 0 || col >= m_columns)
        return;

    m_grid[row][col] = value;
    m_tilesModel.updateTile(row, col, visualTypeFor(value));
}
```

Здесь `visualTypeFor()` должна сопоставлять символ симуляции со строкой для делегата. Не всякое игровое состояние обязательно равно визуальному типу: яма может быть `'.'` в физике, но рисоваться как `"dug"`. Если такое различие важно, лучше хранить отдельное состояние клетки, чем накапливать неочевидные исключения.

### Почему строки не всегда идеальная модель

`QVector<QString>` удобно читать и редактировать на старте. Но когда клетка имеет свойства — таймер восстановления, прочность, вид грунта — одного символа недостаточно. Тогда можно перейти к структуре:

```cpp
enum class TileKind {
    Empty,
    Brick,
    Ladder,
    Rope,
    Crystal,
    Prize
};

struct Cell {
    TileKind kind = TileKind::Empty;
    bool isPerimeter = false;
    qint64 restoreAtMs = 0;
};
```

Преимущества — типобезопасность и явные поля. Недостатки — больше кода для карты, сериализации и сравнения. Не переписывайте проект только ради «более взрослого» вида: переход оправдан, когда текущая модель реально мешает добавить поведение.

### Упражнение 10.1 — маленький безопасный рефакторинг

1. Найдите повторяющиеся пары `setTileAt()` и `updateTile()`.
2. Добавьте одну централизованную функцию изменения клетки.
3. Переведите на неё только одну механику, например сбор приза.
4. Проверьте, что кристалл, яма и периметр не изменили поведение.
5. После успешной проверки переведите остальные места.

Один рефакторинг за раз помогает понять причину регрессии, если что-то пошло не так.

**Проверка:** пауза действительно останавливает все игровые изменения, а не только перемещение игрока.

### Задание C — проигрыш и повторный запуск

**Цель:** разделить новую игру, перезапуск уровня и респавн.

- Опишите, что сохраняется после потери жизни.
- Разделите загрузку карты и возврат сущностей на старт.
- Добавьте `restartGame()` как команду движка.
- Сбросьте терминальные флаги и таймеры без утечек.

**Проверка:** после поражения можно начать заново; собранные предметы соответствуют выбранному правилу.

### Задание D — враги с данными, а не специальными исключениями

**Цель:** освоить модели Qt и небольшие сущности.

### Задание E — конфигурация уровней

**Цель:** уйти от копирования правил при добавлении третьей карты.

- Вынесите общие правила перехода в функцию.
- Проверьте размеры и корректность данных при загрузке.
- Решите, где хранить снимки и когда сбрасывать их при новой игре.

**Проверка:** добавление уровня требует новых данных, но не копии `movePlayer()`.

### Правило проектирования сценария: каждый приз должен быть достижим

При создании уровня вручную размещайте каждый приз так, чтобы персонаж мог до него добраться. Если путь перекрывают кристаллы, оставьте проход сбоку и свободную клетку назначения для разрешённого толкания одного кристалла. Каждый кристалл, который предполагается толкать, должен иметь доступную сторону подхода и свободную клетку назначения. Не собирайте кристаллы в сплошную неподвижную гряду, которая запирает призы или перекрывает путь. Обозначайте сам вход или выход одной клеткой `X`. Клетку подхода кодируйте как `x`: персонаж проходит через неё, физика считает её занятой, но QML рисует обычный пол. Так кристаллы и призы не заслонят сам проход или клетку перед ним, а метка перехода будет только одна. Применяйте эти правила и к проверке карт, созданных генератором.

### Задание E.1 — разработка генератора пейзажей

Разработку генератора ландшафтов стоит выделить в самостоятельный этап курса. Сначала опишите формат результата генератора так, чтобы случайная карта проходила через ту же загрузку, проверку и симуляцию, что и уровни, созданные вручную. Для воспроизводимости генератор должен принимать seed: одна и та же версия алгоритма с одинаковым seed выдаёт одну и ту же карту.

До публикации карты проверяйте её автоматически: прямоугольные размеры, замкнутый периметр, ровно одну стартовую позицию, хотя бы один приз, доступность призов от старта, свободный проход к выходам и отсутствие объектов внутри стен или выходного коридора. Если карта не прошла проверку, генератор должен перестроить её или сообщить понятную ошибку. Не начинайте с полностью случайного заполнения клеток: сначала создайте проходимый каркас комнат и коридоров, затем разместите препятствия и предметы.

**Проверка:** повторная генерация с тем же seed даёт одинаковую карту; разные seed обычно дают разные карты; каждая принятая карта загружается и остаётся проходимой.

## 13. Как расти до уверенного middle

Используйте игровые функции как задачи на инженерный процесс.

### Перед кодом

1. Сформулируйте ожидаемое поведение одним абзацем.
2. Запишите примеры и крайние случаи.
3. Найдите все места, где читаются и меняются затрагиваемые данные (`rg`).
4. Определите инварианты и ответственность каждого класса.
5. Выберите самое маленькое изменение, которое можно проверить отдельно.

### Во время кодирования

- Давайте функциям имена по их контракту.
- Ограничивайте число причин для изменения у одной функции.
- Не скрывайте побочные эффекты в функции с названием вроде `canMove()`.
- Сначала валидируйте, потом меняйте состояние.
- Не добавляйте абстракцию, пока не видите повтор или реальную сложность.
- Комментариями объясняйте **почему**, если причина не очевидна; не пересказывайте строку кода.

### После изменения

1. Скомпилируйте проект.
2. Проверьте обычный и граничный сценарии.
3. Просмотрите `git diff` целиком.
4. Убедитесь, что в diff нет временных логов и случайных файлов.
5. Опишите проверку и известные ограничения.
6. Зафиксируйте небольшую законченную единицу работы отдельным коммитом.

Для каждого Git-коммита в этом проекте используйте русский язык, понятную тему и подробное тело: что изменено, как ведёт себя игра, что проверено. Например:

```text
Сделать сбор призов однократным и синхронизировать HUD

При входе игрока в клетку с призом движок удаляет предмет из сетки,
обновляет соответствующую строку TileModel и увеличивает счёт.
Счётчик оставшихся призов уменьшается ровно один раз, поэтому повторный
вход в клетку не начисляет очки повторно.

Проверено: сбор одного приза, повторный вход в освобождённую клетку,
обновление HUD и сборка проекта.
```

Навык middle растёт через обратную связь. Просите разбирать ваш diff: какие инварианты защищены, какие крайние случаи не проверены, где интерфейс класса слишком широк, а где абстракция преждевременна. После review сначала объясните своими словами каждое замечание, затем исправьте код сами.

## 14. Словарь проекта

**Состояние (state)** — данные, определяющие текущую ситуацию игры: карта, позиция игрока, счёт, призы, враги.

**Представление (view)** — визуальная часть, отображающая состояние. В проекте это QML-элементы и делегаты моделей.

**Модель Qt (model)** — объект, предоставляющий данные представлениям по строкам и ролям, например `TileModel`.

**Делегат (delegate)** — QML-компонент, который создаётся для одной записи модели.

**Привязка (binding)** — декларативное выражение QML, которое пересчитывается при изменении зависимых свойств.

**Инвариант** — условие, которое должно быть верным до и после каждой операции, например «у одного приза не может быть двух клеток».

**Снимок (snapshot)** — копия достаточной части состояния, чтобы восстановить экран в прежнем виде.

**Атомарное изменение** — операция, которая либо полностью применяет переход состояния, либо не меняет его вовсе.

**Дискретная симуляция** — модель, в которой мир меняется отдельными тиками, например раз в 250 мс.

**Регрессия** — поломка ранее работавшего поведения после нового изменения.
