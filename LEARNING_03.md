## 1. Результат и файлы

Генератор должен выдавать уровень, который:

- имеет корректные размеры и закрытый периметр;
- содержит ровно одного Персонажа и хотя бы один обязательный Приз;
- не запирает Персонажа при открытии;
- не запускает физику Кристаллов и Призов до первого решения игрока;
- даёт доступ к выходу после сбора обязательных Призов;
- содержит маршрут, где для получения хотя бы одного Приза необходимо копать;
- остаётся воспроизводимым при повторении с тем же seed.

Ключевые файлы:

| Файл | Ответственность |
|---|---|
| `src/landscapegenerator.h` | Небольшой публичный интерфейс генератора. |
| `src/landscapegenerator.cpp` | Случайные числа, построение карты, размещение объектов и проверки. |
| `src/gameengine.cpp` | Решает, когда вызывать генератор, загружает принятую карту и управляет переходами. |
| `src/gameengine.h` | Объявляет состояние игры и внутреннюю функцию перехода к генерации. |
| `qml/levels/Level1.qml`–`Level5.qml` | Ручные уровни. Их строки передаются в движок при инициализации. |
| `qml/main.qml` | Отображает уровень и объясняет игроку условие перехода. |
| `qml/components/Tile.qml` | Рисует типы клеток, в том числе выход и объекты. |

Начните с чтения `landscapegenerator.h`, затем проследите вызов `LandscapeGenerator::generate()` в `GameEngine::generateNextLandscape()`. Ручные карты находятся отдельно в QML и передаются движку через `initializeLevels()`. После этого вернитесь к `landscapegenerator.cpp` и читайте его сверху вниз.

## 2. Сначала сформулируйте правила карты

Случайная карта не становится хорошей только потому, что в ней много случайных клеток. Сначала задайте обязательные свойства — инварианты. Инвариант генератора должен быть проверяемым условием, а не пожеланием в комментарии.

Для текущего проекта правила можно оформить так:

| Правило | Способ проверки |
|---|---|
| Высота — 13 строк, ширина — 20 клеток | Размер вектора и длина каждой строки. |
| Периметр закрыт кирпичом | Проверка крайних строк и столбцов. |
| На карте один старт | Подсчёт символов `P`. |
| Есть обязательные награды | Подсчёт `$`; в кармане одна награда намеренно требует копания. |
| Есть ровно один выход | Подсчёт `X` и проверка достижимости. |
| На карте ровно 20 Кристаллов | Подсчёт символов `C`. |
| Подвижные объекты не падают сразу | Каждая начальная клетка `C`, `$` или `S` имеет кирпичную опору. |
| У старта есть первый ход | Клетка над `P` свободна. |
| Выходы достижимы | Поиск пути от старта без прохождения сквозь стены и Кристаллы. |
| Кристалл можно сдвинуть | Есть достижимая клетка для подхода и пустая клетка назначения. |
| Один приз требует копания | Проверяются клетка подхода, разрушаемый кирпич и клетка награды. |

Уточните правила до кодирования. Например, что значит «Кристалл доступен»? Для этой игры это не сбор награды, а возможность подойти и вытолкнуть его в сторону. Уточнение превращает двусмысленное требование в проверяемое условие.

## 3. Граница ответственности генератора и движка

Генератор отвечает на вопрос: «Какие строки карты удовлетворяют правилам?» Игровой движок отвечает на вопросы: «Когда создавать карту?», «Как переключить уровень?» и «Как загрузить карту в игровую модель?»

Публичный интерфейс генератора намеренно узкий:

```cpp
class LandscapeGenerator
{
public:
    // Одинаковый seed и неизменные правила дают ту же карту.
    static QVector<QString> generate(quint32 seed, QString *error = nullptr);
};
```

`QVector<QString>` — результат. `seed` — управляющее входное значение. Необязательный `error` позволяет вернуть объяснение, если подходящая карта не найдена. Генератору не нужен `QObject`: он не хранит состояние между уровнями, не испускает сигналы и не отображает интерфейс.

Такой интерфейс даёт возможность независимо развивать алгоритм. Например, генератор не должен вызывать `loadLevel()`, менять `m_playerX` или ссылаться на QML-объект. Иначе генерация окажется сцеплена с жизненным циклом игры и её будет сложнее разбирать.

## 4. Шаг 1. Представление карты

Карта — прямоугольный `QVector<QString>`. Каждый символ задаёт тип клетки или сущность:

```text
# — кирпич       . — пустая клетка
P — Персонаж     X — выход
x — безопасная клетка у выхода
C — Кристалл     $ — обязательный Приз
S — Суперприз
```

Пример фрагмента:

```cpp
QVector<QString> map(13, QString(20, QLatin1Char('.')));
map[0] = QString(20, QLatin1Char('#'));
map[12] = QString(20, QLatin1Char('#'));
```

Координата в строках карты записывается как `[row][column]`. `row` — вертикаль, `column` — горизонталь. В `QPoint` порядок конструктора привычнее читать как `(x, y)`, поэтому код использует `QPoint(col, row)`. Эта разница — частый источник переставленных координат.

Для безопасного обращения к произвольной клетке есть проверка формы:

```cpp
bool isInside(const QVector<QString> &map, int row, int col)
{
    return row >= 0 && row < map.size()
            && col >= 0 && col < map[row].size();
}
```

Проверяйте `row` до `map[row]`: в противном случае сама проверка может обратиться за границы вектора.

## 5. Шаг 2. Воспроизводимая случайность

Обычная случайность затрудняет отладку: после исправления ошибки карта может измениться, и исходный сценарий будет трудно повторить. Seed задаёт начальное состояние последовательности чисел. При одинаковом seed последовательность и карта повторяются, если алгоритм не менялся.

В проекте для этого есть маленький xorshift-генератор:

```cpp
class SeededRandom
{
public:
    explicit SeededRandom(quint32 seed)
        : m_state(seed == 0 ? 0x6D2B79F5u : seed)
    {}

    quint32 next()
    {
        m_state ^= m_state << 13;
        m_state ^= m_state >> 17;
        m_state ^= m_state << 5;
        return m_state;
    }

    int bounded(int upperExclusive)
    {
        return upperExclusive > 0
                ? static_cast<int>(next() % static_cast<quint32>(upperExclusive))
                : 0;
    }

private:
    quint32 m_state;
};
```

Здесь `m_state` — состояние генератора. Каждый вызов `next()` меняет его тремя побитовыми операциями. Нулевое состояние xorshift не меняется никогда, поэтому нулевой seed заменяется ненулевой константой. `bounded(n)` переводит число в диапазон `[0, n)`.

Остаток от деления может давать небольшое смещение распределения, если размер диапазона не делит весь диапазон `quint32`. Для текущей простой игры это удобно и достаточно. В упражнении по качеству случайности можно заменить этот способ на rejection sampling или `QRandomGenerator::bounded()`, передавая локальный экземпляр, а затем сохранить воспроизводимость.

Не используйте глобальный генератор случайных чисел: случайный вызов в интерфейсе или физике тогда может сдвинуть последовательность генерации ландшафта.

## 6. Шаг 3. Надёжный каркас

Сначала постройте геометрию, которая гарантирует старт и выход, и только потом добавляйте вариативность. Полностью случайное заполнение часто производит комнаты без пути, а поиск такого пути требует всё чаще отбрасывать кандидатов.

Базовая последовательность:

```text
1. заполнить карту пустыми клетками;
2. закрыть внешний периметр;
3. поставить Персонажа, выходы и безопасные клетки;
4. создать обязательную комнату с копанием;
5. добавить платформы и простенки;
6. разместить объекты;
7. проверить кандидата.
```

Для внешних стен используется цикл по строкам и отдельные крайние строки:

```cpp
for (int row = 0; row < kRows; ++row) {
    map[row][0] = QLatin1Char('#');
    map[row][kColumns - 1] = QLatin1Char('#');
}
map[0] = QString(kColumns, QLatin1Char('#'));
map[kRows - 1] = QString(kColumns, QLatin1Char('#'));
```

Стартовая область и нижний выход фиксированы, чтобы небольшие случайные изменения не могли случайно стереть основу сценария:

```cpp
map[11][1] = QLatin1Char('X');
map[11][2] = QLatin1Char('x');
map[11][3] = QLatin1Char('P');
map[11][17] = QLatin1Char('x');
map[11][18] = QLatin1Char('X');
```

В цикле платформ случайность меняет проход, а не сам факт существования платформы:

```cpp
const int platformRows[] = {2, 4, 6, 8};
for (int platformIndex = 0; platformIndex < 4; ++platformIndex) {
    const int row = platformRows[platformIndex];
    const int gapStart = 4 + random.bounded(11);
    const int gapWidth = 1 + random.bounded(2);

    for (int col = 2; col <= 17; ++col) {
        const bool inGap = col >= gapStart && col < gapStart + gapWidth;
        if (!inGap)
            map[row][col] = QLatin1Char('#');
    }
}
```

Разрыв шириной 1 или 2 клетки при смещении по платформам создаёт маршрут, который игрок исследует. Но геометрия разрывов должна быть подчинена проверке выхода и доступности наград; визуальная сложность сама по себе недостаточна.

Короткие простенки добавляются только после основного каркаса и не должны случайно закрывать шахту:

```cpp
const bool insideShaft = col >= gapStarts[index]
        && col < gapStarts[index] + gapWidths[index];
if (insideShaft || map[supportRow][col] != QLatin1Char('.'))
    continue;
map[supportRow][col] = QLatin1Char('#');
```

Условие `map[...] != '.'` защищает уже поставленные объекты и специальные клетки. Условие `insideShaft` сохраняет запланированный вертикальный маршрут.

## 7. Шаг 4. Размещение ландшафта и объектов

### 7.1 Сначала соберите допустимые клетки

Не выбирайте координату из всей карты и не пытайтесь потом исправить столкновение удалением предмета. При построении платформ генератор накапливает клетки, где объект можно разместить над опорой:

```cpp
if (col > 2 && col < 17)
    supportedCells.append(QPoint(col, platformRow - 1));
```

Такое множество кандидатов хранит полезное свойство: клетка находится над кирпичной платформой. После выбора всё равно проверьте, что сама клетка свободна:

```cpp
const QPoint cell = supportedCells[random.bounded(supportedCells.size())];
if (map[cell.y()][cell.x()] == QLatin1Char('.'))
    map[cell.y()][cell.x()] = QLatin1Char('C');
```

Проверьте, что список кандидатов непустой до выбора случайного индекса. В текущей геометрии платформы гарантируют его наличие; если вы меняете размеры или число платформ, добавьте явную проверку.

### 7.2 Кристаллы — препятствия, а не награды

В игре `C` не уменьшает счётчик обязательных Призов. Игрок должен иметь возможность подойти к Кристаллу и вытолкнуть его. Поэтому валидатор ищет свободный подход и пустое направление толкания.

Генератор размещает ровно 20 Кристаллов — по пять на каждой платформе:

```cpp
constexpr int targetCrystals = 20;
constexpr int crystalsPerPlatform = targetCrystals / 4;
```

Клетки непосредственно у каждой вертикальной шахты исключены из набора мест для Кристаллов. Это сохраняет входы на платформы. После размещения BFS проверяет доступность Призов и выходов, а проверка каждого Кристалла требует достижимую сторону подхода и свободную клетку толкания. Кандидат без таких лазеек отклоняется целиком. Равномерный лимит не позволяет случайно собрать все препятствия на одной полке.

Следите за совпадением создания и проверки. Если вы изменили диапазон, обновите обе границы в `validateCandidate()`. Иначе генератор будет создавать кандидатов, которые сам же всегда отклоняет, либо пропустит нежелательное число объектов.

### 7.3 Устойчивость физики при открытии экрана

Каждый `$`, `C` и `S` — подвижный объект. Если клетка непосредственно под ним пуста, первый шаг физики может уронить объект до того, как игрок успеет принять решение. Начальная карта требует кирпичную опору:

```cpp
if (tile == QLatin1Char('C') || tile == QLatin1Char('$')
        || tile == QLatin1Char('S')) {
    if (row + 1 >= kRows || map[row + 1][col] != QLatin1Char('#'))
        return fail(QStringLiteral("подвижный объект не имеет кирпичной опоры"));
}
```

Опора делает стартовый объект устойчивым по вертикали, но это не доказывает, что он никогда не сможет катиться. Если боковое перекатывание может произойти при первом обновлении физики, добавьте проверку именно того правила физики, которое способно его вызвать, или проверяйте состояние после симуляции первого шага. Не делайте вывод только по картинке.

### 7.4 Приз за выкапываемым кирпичом

Один приз заложен в нижнем кармане:

```text
строка 10:       # # #       (стены кармана)
строка 11:   ... P . # $ # ...
```

Персонаж должен дойти до клетки `(row 10, column 6)`, выкопать кирпич `(11, 7)` и затем войти в клетку Приза `(11, 8)`. Под Призом находится кирпич, чтобы награда не упала сразу после загрузки.

Этот сценарий создаётся фиксированно, чтобы случайная геометрия не разрушила обязательную обучающую задачу. Когда будете рандомизировать карман, вместе с его генерацией реализуйте проверку подхода, направления копания, открывшейся клетки и устойчивости Приза.

### 7.5 Суперприз

Суперприз появляется с вероятностью `1/4`. После выбора вероятности он помещается в свободную клетку из того же набора поддержанных поверхностей:

```cpp
if (random.bounded(4) == 0) {
    // Собрать свободные поддержанные клетки и выбрать одну.
}
```

У него отдельный символ `S`, отдельное отображение и стоимость 25 очков. Он не входит в `prizesLeft`: обязательное условие уровня сохраняет отдельный набор обычных призов. Это решение согласует механику и интерфейс: необязательный бонус не блокирует выход.

### Упражнение 7.1 — новый объект

Добавьте новый тип объекта по цепочке:

1. выберите символ карты;
2. определите, является ли объект препятствием, наградой или подвижной сущностью;
3. опишите допустимые клетки размещения;
4. добавьте проверку опоры и доступности;
5. научите `GameEngine::loadLevel()` распознавать символ;
6. добавьте обработку взаимодействия в движок;
7. добавьте отображение в `Tile.qml`;
8. вручную проверьте счёт, физику, сохранение уровня и переходы.

## 8. Шаг 5. Проверка кандидата

`validateCandidate()` — граница между «похоже на карту» и «разрешено загружать в игру». Функция не должна менять кандидата. Она отвечает `true` для принятой карты и записывает короткое объяснение отказа для остальных.

Первым делом проверяется форма. Это защищает следующие циклы и обращения к индексам:

```cpp
if (map.size() != kRows)
    return fail(QStringLiteral("неверное количество строк"));
for (const QString &row : map) {
    if (row.size() != kColumns)
        return fail(QStringLiteral("строки карты имеют разную ширину"));
}
```

Затем проверяется периметр, подсчитываются `P`, `$`, `C`, `S`, `X`, и для объектов проверяется опора. Каждая проверка должна соответствовать конкретному игровому правилу.

### 8.1 Поиск достижимых клеток

Поиск в ширину (BFS) отвечает на вопрос: можно ли пройти от старта по соседним клеткам. Очередь хранит клетки, которые надо обработать; множество `visited` не даёт заходить в одну клетку повторно.

```cpp
QSet<int> visited;
QQueue<QPoint> queue;
visited.insert(cellKey(start));
queue.enqueue(start);

while (!queue.isEmpty()) {
    const QPoint current = queue.dequeue();
    for (const QPoint &direction : directions) {
        const QPoint next = current + direction;
        if (!isInside(map, next.y(), next.x())
                || visited.contains(cellKey(next)))
            continue;

        const QChar tile = map[next.y()][next.x()];
        if (tile == QLatin1Char('#') || tile == QLatin1Char('C'))
            continue;

        visited.insert(cellKey(next));
        queue.enqueue(next);
    }
}
```

Стены и Кристаллы здесь препятствия. BFS не моделирует толкание, копание, гравитацию и состояния после каждого действия. Это важно: проверка должна честно описывать свою модель. Для толкания есть отдельное упрощённое условие; для сложной физики в будущем понадобится симулятор действий или поиск по состояниям мира.

`cellKey()` кодирует координаты в одно число:

```cpp
int cellKey(QPoint cell)
{
    return cell.y() * kColumns + cell.x();
}
```

Ключ корректен только при известной ширине карты. Если генератор станет поддерживать размеры из параметров, передавайте ширину в функцию или храните координаты с подходящим хешем.

### 8.2 Проверка толкания Кристалла

Для Кристалла в столбце `col` проверяются два направления. Например, чтобы толкнуть вправо, Персонаж должен добраться до клетки слева, а клетка справа от Кристалла должна быть пустой:

```cpp
const int approachCol = col - direction;
const int destinationCol = col + direction;
if (reachable.contains(row * kColumns + approachCol)
        && map[row][destinationCol] == QLatin1Char('.')) {
    canPush = true;
}
```

Проверка не гарантирует, что игрок сможет выйти из тупика после каждого толчка. Это ограничение упрощённой модели. Улучшение для самостоятельной работы — проверять безопасную клетку за Кристаллом и наличие следующего маршрута после его перемещения.

### 8.3 Проверка выхода и обязательного копания

Каждый `X` должен находиться в наборе `reachable`. Для специального приза проверяется другая последовательность: доступен подход, кирпич на месте, награда и боковая стена занимают ожидаемые клетки. Такой отдельный контракт предотвращает случайное превращение обязательной головоломки в недостижимую декорацию.

Добавляя новое правило, ответьте на три вопроса:

1. Где его проверять — при размещении или в финальном валидаторе?
2. Может ли существующая карта нарушить его после изменения другого правила?
3. Каково точное сообщение об отказе, помогающее найти причину?

Проверки на этапе размещения экономят случайные попытки. Финальная валидация нужна даже при аккуратном размещении: позже соседнее изменение может нарушить прежнее допущение.

## 9. Шаг 6. Повторные попытки и ошибки

Генератор пробует ограниченное число кандидатов. Для каждой попытки используется производный seed:

```cpp
for (quint32 attempt = 0; attempt < 32; ++attempt) {
    const quint32 attemptSeed = seed + attempt * 0x9E3779B9u;
    QVector<QString> candidate = createCandidate(attemptSeed);
    QString reason;
    if (validateCandidate(candidate, &reason))
        return candidate;
}
return {};
```

Почему не бесконечный цикл? Если ограничения стали противоречивыми, бесконечная генерация зависнет. Фиксированный лимит гарантирует завершение и делает ошибку видимой.

В текущем коде `error` получает причину последнего отклонённого кандидата. При дальнейшем развитии полезно хранить частоты причин: например, сколько раз карта отвергнута из-за недостижимого выхода и сколько — из-за Кристалла. Это помогает выявить чрезмерно жёсткое правило.

`GameEngine::generateNextLandscape()` вызывает генератор только при входе в правый выход после сбора обязательных призов. При пустом результате текущий уровень не заменяется. Позиция остаётся рядом с выходом, чтобы игрок мог повторить попытку после следующего действия.

### Упражнение 9.1 — понятный отказ

Временно добавьте намеренно невозможное правило, запустите генерацию с фиксированным seed и прочитайте `error`. Убедитесь, что приложение не теряет текущую карту. После этого отмените искусственное правило.

## 10. Шаг 7. Подключение генератора к игровому циклу

Путь к новому экрану выглядит так:

```text
Персонаж собрал все обязательные Призы
        ↓
prizesLeft становится равен 0
        ↓
выход визуально подсвечивается, но переход не запускается сам
        ↓
Персонаж входит в X в правом нижнем углу
        ↓
GameEngine проверяет условие перехода
        ↓
generateNextLandscape() вызывает LandscapeGenerator::generate(seed)
        ↓
успешная карта добавляется в список уровней и загружается
```

Разница между доступностью выхода и переходом важна для управления: сбор приза сообщает, что цель выполнена, а переход происходит только после действия игрока. Это предотвращает внезапную смену экрана во время движения или обновления физики.

При создании следующей карты движок сохраняет текущий уровень. Новая карта добавляется в историю, а не заменяет предыдущую. Левый портал поэтому возвращает к предыдущему экрану и его сохранённому состоянию.

Seed хранится внутри движка и не выводится на игровые кнопки. Для отладки генератор всё равно принимает seed напрямую. В будущем можно добавить диагностический журнал или отдельную команду разработчика, не смешивая её с обычным управлением игрока.

### Упражнение 10.1 — проверьте путь события

Проследите в исходниках один переход от нажатия клавиши до `loadLevel()`. Найдите, какие сигналы уведомляют QML о новом уровне, и проверьте, что модель клеток обновляется после загрузки. Объясните, почему генератор не меняет QML-модель напрямую.

## 12. Ручная проверка и разбор ошибок

Сборка проверяет компиляцию C++ и упаковку QML, но сама по себе не доказывает правильность алгоритма. Для генератора используйте фиксированные сценарии ручной проверки:

1. Повторите один seed — строки должны совпасть.
2. Возьмите несколько разных seed — рельеф или расположение предметов должны отличаться.
3. Откройте уровень и убедитесь, что Персонаж может сделать первый ход.
4. Наблюдайте за объектами сразу после открытия: Кристаллы и Призы не должны самопроизвольно начать падать.
5. Проверьте, что выход можно достичь после сбора всех обязательных Призов.
6. Проверьте маршрут через копание к специальному Призу.
7. Толкните каждый тип объекта в доступном направлении и убедитесь, что он не застрял из-за очевидной ошибки размещения.
8. Соберите обычный Приз и Суперприз: проверьте стоимость и счётчик обязательных наград.
9. Вернитесь через левый портал и убедитесь, что предыдущий экран сохранился.

Это сценарии проверки поведения, а не доказательство корректности всех возможных карт. Когда вы освоите базовую реализацию, превратите проверяемые инварианты в автоматические тесты для большого набора seed.

### Как читать ошибку валидатора

Если карта постоянно отвергается:

1. зафиксируйте seed;
2. выведите причину отказа;
3. выведите строки кандидата до проверки;
4. найдите правило, которое нарушено;
5. проверьте, не противоречат ли два правила друг другу;
6. исправьте либо построение кандидата, либо чрезмерно узкое ограничение;
7. удалите временную диагностику или оформите её как контролируемый debug-вывод.

Не ослабляйте валидатор только ради того, чтобы генерация перестала возвращать ошибку. Сначала выясните, почему кандидат не удовлетворяет игровому контракту.

## 13. Как расширять генератор дальше

Когда текущие правила станут понятны, развитие можно вести по слоям:

1. **Параметры сложности.** Явно передавать диапазоны платформ и объектов.
2. **Комнаты и коридоры.** Генерировать граф связности комнат, затем рисовать его на сетке.
3. **Поиск маршрута с действиями.** Представлять состояние как карту плюс позицию Персонажа; переходы поиска включают ходьбу, копание и толкание.
4. **Симуляция физики-кандидата.** Проверять изменения после первого и последующих шагов физики.
5. **Оценка качества.** Считать длину пути, число развилок и сложность добычи наград; принимать карты в заданном диапазоне качества.
6. **Диагностика.** Сохранять seed, карту и причины отклонений в журнал для воспроизведения ошибок.
7. **Отделение данных от алгоритма.** Вынести легенду, размеры и параметры уровней в структуры или формат данных, когда ручное дублирование станет источником ошибок.

Не начинайте с «умного» генератора. Сначала доведите до ясности простой цикл: создать каркас → разместить предметы → проверить инварианты → принять или отклонить. Усложняйте модель только тогда, когда можете показать, какое ограничение текущая модель не способна выразить.

## 14. Словарь

- **Кандидат** — временно созданная карта, которая ещё не прошла валидацию.
- **Инвариант** — свойство, обязательное для каждой принятой карты.
- **Seed** — начальное состояние псевдослучайной последовательности.
- **Детерминированность** — одинаковые входные данные дают одинаковый результат.
- **BFS / поиск в ширину** — обход соседних клеток слоями для проверки достижимости.
- **Поддержанная клетка** — позиция объекта с опорой снизу по текущему правилу.
- **Валидатор** — функция, которая принимает или отклоняет кандидата по формальным правилам.
- **Ложное допущение** — условие, которое код считает истинным, хотя оно не гарантировано, например «опора снизу исключает любое движение объекта».
